# Log: transport-framing

Implemented the first RUI-style AVC USB debug protocol slice in firmware and host tools.

Firmware/protocol changes:

- Added shared C/C++ wire header `src/common/avc_usb_debug/avc_usb_debug_protocol.h`.
- Added `src/common/avc_usb_debug` to the AVC `.cproject` include paths; the CMake wrapper regenerated `src/avc/avc_core0/cmake/mcuxpresso_debug.cmake` with that include directory.
- Replaced the temporary frame-chunk header in `avc_usb_debug_stream.c` with a 32-byte `AVCU` envelope carrying `msg_id = AVC_DBG_RUI_WRITE_FRAME_BUFFER_RAW`.
- Added a 24-byte RUI raw-framebuffer chunk payload header with frame id, byte offset, total bytes, geometry, pixel format, buffer id, and chunk flags. Raw RGB565 bytes follow that header.
- Kept the current ASCII `START`/`STOP` commands for bring-up; binary control messages are reserved in the shared header but not yet exercised.

Host-tool changes:

- Updated the native C++ receiver to include the shared protocol header and validate envelope/message/chunk fields.
- Updated the Python receiver and WebSerial viewer to parse the new RUI-style packet format.
- Changed receiver default read size to 256 KiB and documented why.

Validation:

- `./build_cmake.ps1` passed and linked `avc_core0.axf`.
- `./flash.ps1 -CMake` flashed the protocol-updated AVC firmware.
- COM15 re-enumerated as `USB Serial Device`, `VID_1FC9&PID_0094`.
- Native receiver, explicit 256 KiB reads: `34.377 MiB/s`, `280.66 fps` equivalent, `0` malformed headers, `0` sequence errors over 10 seconds.
- Python receiver, explicit 256 KiB reads: `33.566 MiB/s`, `274.03 fps` equivalent, `0` malformed headers, `0` sequence errors over 10 seconds.
- Native receiver default run: `32.138 MiB/s`, `262.42 fps` equivalent, `0` malformed headers, `0` sequence errors over 10 seconds.
- Native receiver build, Python `--help`, and `node --check src/usb_debug_host/webserial_viewer.js` passed.

Host read-size finding:

- 1 MiB reads can show apparent Windows CDC serial gaps under sustained max-rate streaming with this protocol, while 256 KiB reads are clean and still above 30 MiB/s. Treat 256 KiB as the current recommended Windows CDC measurement setting unless the host path is revalidated.

Interpretation:

- The base transport is now functional and extensible in the RUI direction. The remaining `transport-framing` work is to exercise binary control, add text/log/stats packets, and decide how much of the protocol constants should be generated or shared into Python/JS.
