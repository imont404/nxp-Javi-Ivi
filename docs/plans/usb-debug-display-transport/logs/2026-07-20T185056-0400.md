# Log: transport-framing

Reviewed prior Wavenumber/Cricket framing references for the AVC USB debug transport direction:

- `modules/e/src/e_msg.c/.h`: byte-stream envelope with four sync bytes, 16-bit payload length, CRC16, timeout/resync, and a user payload handler.
- Bunny `rui.c/.h`: remote framebuffer operation shape, especially `write_frame_buffer_raw` with start byte index, length, and payload bytes.
- Cricket `rio.c/.h` plus `e_msg_types.h`: 32-bit message ID namespace with RUI and RIO class ranges, fixed operation structs, and response framing through `e_msg__frame_into_q`.

Conclusion: keep the separation of generic transport envelope and typed remote operations. Do not copy `e_msg` directly into the HS USB data path because its byte-at-a-time parser, 16-bit length, and required CRC are not ideal for 30+ MiB/s USB bulk. Instead, keep an `AVCU` transport envelope with a 32-bit `msg_id` and length/sequence fields, and define RUI-style payloads for framebuffer chunks, geometry, present, text, logs, stats, and controls.

Added `docs/research/AVC_USB_Debug_Transport_Protocol.md` as the draft protocol document and linked it from the active plan source-material list. It defines the intended 32-bit message class ranges, a 32-byte base envelope, RUI geometry, raw framebuffer chunk, present, text/log, and control direction. It also notes that final wire constants should move into a shared header under `src/common` once framing is locked, so AVC firmware and native host tooling can include the same source of truth and the bunny effort can coordinate later.
