# SCK raised: 37.20 ms to 17.75 ms per frame, pending a visual check

Measured on hardware. **Not yet verified visually - that needs eyes on the panel.**

## What changed

`CONFIG__DISPLAY_SPI_PLLCLKDIV` sets PLLCLKDIV next to its only consumer, the
display driver. At 1 the LPSPI source becomes 150 MHz instead of 75 MHz.
`CONFIG__DISPLAY_SPI_SCKDIV` sets the divider directly instead of trusting the
SDK baud-rate search.

Both default to the Rev A verified values, so the competition image is unchanged
until someone confirms the picture.

## Results

| Config | ms/frame | Wire time | Efficiency | Budget | Headroom |
|---|---|---|---|---|---|
| 37.5 MHz, as found | 37.20 | 32.77 | 88% | 91% | 3.8 ms |
| 37.5 MHz, init fixed | 34.14 | 32.77 | 96% | 83% | 6.9 ms |
| **50 MHz** | **25.69** | 24.58 | 96% | 63% | **15.3 ms** |
| **75 MHz** | **17.75** | 16.38 | 92% | 43% | **23.2 ms** |

From the starting point, 75 MHz recovers **19.45 ms per frame**. Student
headroom goes from under 4 ms to over 23 ms - from "the budget is gone before
your code runs" to "you have most of the frame".

## A wrong conclusion, corrected

An intermediate run showed 24.96 ms per frame while the register read-back
claimed 75 MHz, and I concluded the transfer was DMA feed-limited at ~49 Mbps.
**That was wrong.** Setting `SCKDIV` explicitly produced 17.75 ms at 96%
efficiency, so the feed keeps up fine.

What actually happened: the run was at 50 MHz, correctly chosen by the SDK
search, and the *read-back* was misreporting.

## The read-back is unreliable - do not trust it

`lpspi1_report_clock()` prints `sckdiv=0` in every configuration, including ones
whose measured throughput proves `SCKDIV` is 1:

```
CCR=00000000 TCR=0040001F CFGR1=00000001
```

`CCR` reads back as zero even when the divider is demonstrably in effect. `TCR`
decodes correctly - `FRAMESZ=31` for 32-bit, `BYSW=1` - so the read path itself
works.

Timing is ground truth; the register read is a claim that failed. The cause is
not yet established. A plausible candidate is `LPSPI_PrepareTransferEDMA()`
inside `PrepareEDMALite`, which the frame-size switch calls, but that is a guess
and is written here as one.

This also means the earlier `confirm-spi-clock` conclusion was **right for the
wrong reason**. 37.5 MHz was correct - it matches the clock tree and the wire
time - but the `sckdiv=0` that appeared to confirm it may have been the same
misreport.

## What is not verified

**Nobody has looked at the screen.** At 75 MHz the panel flex is being driven
twice as fast as the Rev A verified rate, and signal integrity failure there
shows up as sparkle or torn pixels while every number here still looks perfect.

The LPSPI module maximum from the MCXN947 datasheet is also still unchecked.
Feeding the peripheral 150 MHz does not license clocking SCK at 75.

The board is currently running the 75 MHz build so it can be inspected. If it
looks wrong, 50 MHz is the fallback and still recovers 11.5 ms.

## Next

Visual check, then the datasheet ceiling. If 75 MHz is clean, the remaining
work - polled control bytes and the single-TCD dump - is worth about 1.35 ms
against a dump that would then be 17.75 ms.
