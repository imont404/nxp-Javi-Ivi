# PLLCLKDIV=1 breaks the display, and the instrumentation is unsound

`raise-spi-clock` stays **pending**. The board is back on the competition image
and confirmed working on screen.

## The discriminating result

| Build | SCK | Screen |
|---|---|---|
| `PLLCLKDIV=2`, `SCKDIV=-1` (committed default) | 37.5 MHz | **works** |
| `PLLCLKDIV=1`, `SCKDIV=0` | 75 MHz | black |
| `PLLCLKDIV=1`, `SCKDIV=1` | 50 MHz | black |
| `PLLCLKDIV=1`, `SCKDIV=2` | **37.5 MHz** | **black** |

The last row is the one that matters. **Same SCK as the working configuration,
only the PLL divider differs, and it fails.** So the fault is `PLLCLKDIV=1`
itself, not the SPI rate, and nothing about panel signal integrity has actually
been established. 50 MHz was never tested at a working divider.

## A conclusion that was wrong

An earlier log recorded that PLLCLKDIV is "effectively private to the LCD",
based on the tree containing exactly one `kPLL_DIV_to_*` attachment. Hardware
contradicts it.

The grep was true and the inference from it was not. One thing it missed:
`clock_config.c:295` carries a `PLLCLKDIV_HALT` setting, so the divider has a
halt behaviour that the board configuration establishes at boot and that a
later `CLOCK_SetClkDiv()` may not reproduce. That is a lead, not a diagnosis.

## The instrumentation cannot be trusted

`main.c:119` - `avc__next_frame()` executes `CYCLE_COUNTER = 0` on every camera
frame. That is the **same DWT counter** the timing macros read. Any measurement
spanning a frame callback is corrupted, which is what the all-zero reports are.

So the headline figures - 37.20 ms baseline, 34.14 ms after the init fix, and
the per-phase split - are **suspect**. They agreed with independently computed
wire time to within a few percent, which is genuine reassurance and suggests
they are broadly right, but agreement is not proof and they were presented as
settled without checking what else wrote to that counter.

Before any further measurement, the instrumentation needs its own time source.

## What still stands

- **The init fix is good.** The display works with it at 37.5 MHz, confirmed on
  screen. Removing the per-frame `EDMA_Init()` on a DMA controller shared with
  the camera is a correctness fix whose value does not depend on the timing
  numbers.
- **The two clock knobs are harmless as committed**, both defaulting to the
  verified Rev A values.

## Next

1. Give the timing instrumentation a private counter, then re-establish the
   baseline honestly.
2. Understand `PLLCLKDIV_HALT` and why a runtime divider change differs from the
   boot-time one, before touching the divider again.
3. Only then revisit whether 50 MHz is reachable, since it has not really been
   tried.
