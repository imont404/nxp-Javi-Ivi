# Per-frame re-initialisation removed: 3.06 ms recovered

Step `split-init-from-reconfigure` done, measured on hardware.

## What changed

`lpspi1_init()` now does its expensive work once, guarded by a static flag.
Later calls fall through to a new `lpspi1_set_frame_size()`, which is the whole
point of the call: the display alternates 8-bit control bytes with 32-bit pixel
words, and nothing else about the peripheral changes.

The mechanism is simple once the SDK is read rather than assumed. Both
`LPSPI_MasterTransferEDMALite` and `LPSPI_MasterTransferPrepareEDMALite` read
`bytesPerFrame` back out of `TCR[FRAMESZ]` at call time - they do not cache it
from `LPSPI_MasterInit`. So a mode switch is a `TCR` write plus a re-prepare to
refresh the handle's `bytesEachWrite`/`bytesEachRead`. `PrepareEDMALite` only
rewrites `CONT`, `CONTC`, `BYSW` and `PCS`, so it preserves `FRAMESZ`.

The module is disabled around the `TCR` write. With LPSPI enabled a `TCR` write
enqueues a command rather than taking effect directly, which is not what a mode
change between transfers wants.

## Result

| Phase, per call | Before | After |
|---|---|---|
| `lpspi1_init(8)` | 769 us | **5 us** |
| `LCD_SetPos` | 356 us | 355 us |
| `lpspi1_init(32)` | 770 us | **6 us** |
| block loop | 16,706 us | 16,703 us |
| total | 18,602 us | **17,070 us** |

Per frame, two calls: **37.20 ms to 34.14 ms - 3.06 ms recovered**, against
3.08 ms predicted from the baseline. The prediction and the measurement agree to
20 us.

Frame budget share drops from 91% to 83%.

## Correctness, not just speed

The removed `EDMA_Init(DMA0, ...)` was resetting the entire DMA controller four
times per frame, and **DMA0 is shared with the camera**. That was a latent
hazard independent of the timing win, and it is now gone.

## How the change was verified without eyes on the panel

Nobody was at the bench, so "the display still looks right" was not available.
Timing alone does not discriminate here - a frame size stuck at 8 bits would
move the same number of bits and take the same wire time.

Added `lpspi1_get_frame_size()`, which reads `TCR[FRAMESZ]` back, and reported
it once per run after each mode switch:

```
lcd_dump framesz control=8 pixel=32 bits
```

That proves the switch takes effect in both directions. It does not prove the
image is correct - byte order, window placement and colour still need a human
look, and that remains open for `verify-and-document`.

## Also

The competition image builds unchanged with the diagnostic off, and the L0
suite passes. The instrumentation macros compile to nothing in that
configuration.
