# Baseline measured: the LCD dump eats 91% of the frame budget

Step `measure-baseline` done. Measured on hardware, competition configuration
plus the timing knob, EZH camera capture, 320x240 panel.

## Method

`CONFIG__DISPLAY_TIMING_DIAG_ENABLE` instruments `eGFX_DumpRaw` with the
existing `CYCLE_COUNTER` (DWT CYCCNT, 150 MHz, 6.67 ns resolution), accumulating
each phase over 48 calls and reporting over RTT. Off by default; the competition
image is unchanged.

`CONFIG__FORCE_TEST_MODE` was added because the LCD refresh path only runs when
the TEST switch (P3_18) is held, and nobody was at the bench. It cannot move the
car: `testmode__motors_enable` starts at 0 and is only set by a center-button
press.

One correction to the measurement itself. `lpspi1_transfer_block()` returns on
*submit* and waits for the *previous* transfer on the way in, so timing the
block loop alone stops one transfer early. Added `lpspi1_wait_idle()` so the
figure covers pixels actually reaching the panel.

## Numbers

Per `eGFX_DumpRaw` call, averaged over 48 calls, stable across eight reports:

```
lcd_dump n=48 avg_us total=18602 init8=769 setpos=356 init32=770 blocks=16706 blks=10 overhead_us=1896
```

The competition path calls it **twice per frame** - once for the 40-row overlay,
once for the 200-row camera view - so per frame:

| Phase | Per frame | Note |
|---|---|---|
| `lpspi1_init(8)` | 1.54 ms | 2 calls |
| `LCD_SetPos` | 0.71 ms | 22 single-byte transfers |
| `lpspi1_init(32)` | 1.54 ms | 2 calls |
| block loop | 33.41 ms | 20 transfers, 153,600 bytes |
| **total** | **37.20 ms** | **91% of the 41 ms budget** |

## What this changes

**The overhead is 3.79 ms per frame, not the estimated 500 us - roughly eight
times larger.** Splitting it:

- **3.08 ms is the four `lpspi1_init()` calls**, at ~770 us each. This is the
  dominant recoverable cost, and it is pure re-initialisation of the LPSPI
  peripheral and the whole DMA controller.
- **0.71 ms is `LCD_SetPos`**, 22 single-byte transfers at ~32 us each.

**The bulk transfer is already near optimal, which is the useful surprise.** At
37.5 MHz the wire time for 153,600 bytes is 32.77 ms. Measured 33.41 ms, so the
block loop runs at 98% efficiency - only 0.64 ms of gap across 20 transfers,
which is 32 us each and matches the per-transfer setup cost exactly.

That consistency is worth noting: **every `lpspi1_transfer_block()` call costs
~32 us regardless of size.** 42 transfers per frame at 32 us is 1.34 ms, and
4.43 ms of total excess minus 3.08 ms of init leaves 1.35 ms. The model closes.

## Consequences for the plan

**The ceiling on the structural work is 4.4 ms.** Removing every init and every
redundant transfer takes the frame from 37.20 ms to about 32.8 ms - the wire
time - and no further. That is a 12% improvement and it is worth having, but it
does not change the shape of the problem.

**The clock remains the only lever that matters.** At 75 MHz the wire time
halves to 16.4 ms, and combined with the structural work the frame dump would go
from 37.2 ms to roughly 17 ms. That recovers 20 ms of a 41 ms budget.

Right now students have **under 4 ms** of headroom for their own algorithm and
overlay drawing after the display dump. That explains the observed behaviour of
teams blowing the frame time when they draw too much - they are not being
careless, the budget is nearly gone before their code runs.

## Correction to the plan text

The plan assumed `eGFX_Dump` and a single full-screen window. The competition
path uses `eGFX_DumpRaw` twice with **different** windows - rows 0-39 and rows
40-239 - so `hoist-window-setup` cannot hoist the window to init as written. The
window still has to be set twice per frame; what can go is the 11-DMA-transfer
implementation, replaced by a prebuilt byte sequence per region pushed through
the FIFO.

## Next

`split-init-from-reconfigure` is now clearly the highest-value structural step,
worth 3.08 ms on its own. `confirm-spi-clock` is the one that decides whether
this optimisation is worth 4 ms or 24 ms.
