# Log: encoder-signal-diag

**QDC encoder hardware verified on both motors.** First hardware run of this
code — it had been build-validated only since 2026-07-21.

Car on blocks. J-Link pinned to 1066857635 throughout.

## Hand-spin, motors off

Both QDC channels count.

| | M0 (J17, QDC0) | M1 (J11, QDC1) |
|---|---|---|
| Counts logged | 4225 | 5558 |
| Peak rate | 1224 cps | 1448 cps |

`IMR` cycles through `0x00`, `0x44`, `0x88`, `0xCC` on both channels — all four
A/B phase states present, so quadrature decoding is genuinely valid rather than
counting noise on one edge.

**Exit criteria met:** `qdc-routing-known` was already met; this settles
`bench-signal-visibility` and `dual-encoder-counts`.

## Motors on, 10% PWM

Center button toggles. 173 samples with motors running.

| | mean counts/sec | sd | min | max |
|---|---|---|---|---|
| M0 | 677.9 | 3.07 | 672 | 688 |
| M1 | 739.4 | 2.73 | 732 | 744 |

**Remarkably stable** — standard deviation under 0.5% of mean on both, with no
overflow or error flags (`f=0000/0000` throughout). Open-loop telemetry is
easily clean enough to support PID tuning, which settles
`speed-control-feasible`.

### The motors do not match

**M1 runs 8.8% faster than M0 at identical PWM.** That is a real mismatch, not
measurement noise — the standard deviations are tiny and the gap held across
the whole run.

Consequences worth carrying:

- A car commanded straight in open loop **will curve.** This is the concrete
  justification for closed-loop wheel speed control, and a good thing to show
  students rather than assert.
- It also means the active-differential idea has to work against a baseline
  asymmetry, not from a symmetric starting point.

## Counts per wheel revolution — still not settled, but the evidence leans

`CONFIG__MOTOR_ENCODER_COUNTS_PER_WHEEL_REV` remains `0`, so `rpm_m` reads 0.
The vendor contradicts itself: spec table says 1:90, support answer says 1:30.

Interpreting the motors-on data both ways:

| | if cpr=1320 (1:30) | if cpr=3960 (1:90) |
|---|---|---|
| M0 | 30.8 rpm, 0.121 m/s | 10.3 rpm, 0.040 m/s |
| M1 | 33.6 rpm, 0.132 m/s | 11.2 rpm, 0.044 m/s |

The motor is rated **110 rpm no-load at 12 V**. At 10% PWM a crude linear guess
is ~11 rpm, which matches **cpr=3960** closely and makes cpr=1320 imply ~28-30%
of no-load speed at 10% duty.

**This favours 1:90 / 3960, i.e. the spec table rather than the support answer.**
Treat it as suggestive only — PWM duty is not linear in speed, especially at
10%, and this is inference from a rated figure rather than a measurement.

**The definitive test remains a counted hand-spin:** mark a wheel, turn it
exactly ten revolutions with motors off, read the position delta. Ten turns
gives 13200 or 39600 — unmistakable.

## Wrapper bugs found and fixed

- Both diagnostic images were written to the same build directory, so whichever
  was built last silently replaced the other. Bad for a build whose motors-on
  variant spins wheels. Now separate directories, with `-EnableMotors` on both
  the build and flash wrappers.
- `flash_motor_encoder_diag.ps1` and `rtt_motor_encoder_diag.ps1` **splatted an
  array**, which passes elements positionally, so `-File` bound to
  `flash.ps1`'s `-Configuration` and the call failed validation. These wrappers
  had never successfully run. Fixed to splat hashtables; both now also take
  `-UsbSerial` and refuse to run if the image is missing.
