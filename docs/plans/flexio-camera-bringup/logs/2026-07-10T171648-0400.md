# Log: flexio-frame-buffer

All OV5640 data lines have been attached to the Port 4 FlexIO data bus.

Hardware state:

- `D0 -> P4_12 / FLEXIO0_D20`
- `D1 -> P4_13 / FLEXIO0_D21`
- `D2 -> P4_14 / FLEXIO0_D22`
- `D3 -> P4_15 / FLEXIO0_D23`
- `D4 -> P4_16 / FLEXIO0_D24`
- `D5 -> P4_17 / FLEXIO0_D25`
- `D6 -> P4_18 / FLEXIO0_D26`
- `D7 -> P4_19 / FLEXIO0_D27`
- Sync remains `PCLK -> P4_20`, `HSYNC/HREF -> P4_21`,
  `VSYNC -> P4_22`.

Visual observation:

The image is fundamentally working and looks pretty good. Color and image
content changed visibly as each data wire was added. There may still be one or
more adjacent pair swaps, such as `D0/D1`, because the header/wiring area is
tight.

RTT observation:

Two short RTT samples after all data lines were connected showed live nonzero
frame data:

- `cam_dma done` continues to advance at about 30 frames/sec.
- `sample_nz=64`, so the sampled first 64 RGB565 words are all nonzero.
- Representative first words included values such as
  `8CAE,86B5,9FB8,9FB8` and `9FB7,9FB8,9F99,9FB9`.
- `submit_err=0` and `cb_err=0`.
- The timeout counter was already at `5`, likely accumulated while data lines
  were being added with the app running, and did not increase during the final
  post-wiring stability sample.

Interpretation:

The FlexIO/eDMA capture path is no longer just a black-frame timing proof. It is
capturing real OV5640 data into the AVC frame buffers and displaying it through
the existing LCD path. Remaining work is validation and refinement: verify data
bit order, byte order, signal integrity, and whether any debug instrumentation
is needed before locking the wiring down.
