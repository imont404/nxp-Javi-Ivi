# Log: OSTIMER Frame Timing Instrumentation

Implemented better frame timing for the FlexIO eDMA camera backend.

The first attempt used free-running CTIMER timestamp reads, but CTIMER3 and
CTIMER2 both reached `camera__configure_frame_timing()` and then stalled inside
the SDK `CTIMER_Init()` reset path before the timing init returned. `CTIMER0`
is already used by `avc__adc.c` for the ADC trigger, so it was not reused for
camera timing.

The active implementation now uses `OSTIMER0` instead:

- Selects `kCLK_1M_to_OSTIMER` and enables `kCLOCK_OsTimer`.
- Reads the 42-bit OSTIMER Gray-code counter and converts it to binary.
- Uses the low 32 bits for short VSYNC, DMA-arm, and DMA-frame deltas.
- Keeps `e_tick__get_ms()` as the report cadence source so RTT summaries do not
  depend on the high-resolution timer.

Validation:

- CMake build passed.
- Flash passed with J-Link V9.54.
- Breakpoint at `camera__configure_flexio_edma_pins()` after timing init
  confirmed `g_camera_timing_clock_hz = 1000000` and a live OSTIMER count.
- RTT captured:
  `FlexIO camera timing: OSTIMER0 free-running at 1000000Hz for VSYNC/DMA timestamps`.

Corrected RTT timing after Gray-code conversion showed steady `cam_dma` reports
with approximately:

- `done=+24` over about `1.026 s`, or `fps=23.39`.
- `vs_us` last value around `42,750 us`.
- `arm_us` around `16 us`.
- `frame_us` around `42,410 us`.
- No new submit or callback errors during the sample window.

One startup timeout and three busy-VSYNC events were present in the lifetime
counters, but they did not continue increasing in the steady sample. The active
firmware still reports the configured capture size as `320x200`; verify the
OV5640 mode separately before assuming the pipeline is running at `320x240`.
