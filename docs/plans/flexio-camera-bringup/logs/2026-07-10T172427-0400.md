# Log: capture-instrumentation-cleanup

Added a dedicated plan step for FlexIO camera code cleanup, counter cleanup, and
timing/FIFO evidence before final comparison against SmartDMA/EZH.

No I/O pins changed in this step. The diagnostics work assumes the current
validated wiring remains:

- `D0-D7 -> P4_12..P4_19 / FLEXIO0_D20..D27`
- `PCLK -> P4_20 / FLEXIO0_D28`
- `HSYNC/HREF -> P4_21 / FLEXIO0_D29`
- `VSYNC -> P4_22 / GPIO IRQ frame-start trigger`

Code analysis:

- `src/common/e/src/e_tick.c` owns `SysTick_Handler` through the
  `CONFIG__E_TICK_IRQ_HANDLER_NAME` macro.
- `src/common/e/src/port/nxp__mcxn/e_port__nxp__mcxn.h` sets
  `CONFIG__E_TICK_PERIOD__MS` to `1` and configures SysTick from
  `SystemCoreClock`.
- The current `cam_dma` line in
  `src/avc/avc_core0/source/avc_io/bv_camera__interface.c` is rate-limited by
  frame-count thresholds. It reports deltas such as `done +30`, but it does not
  yet divide by elapsed time.
- The current `busy_vs` field is a lifetime count of VSYNC edges seen while DMA
  was busy. A separate consecutive-busy counter drives timeout aborts. The RTT
  line should distinguish lifetime totals, report-window deltas, and the
  consecutive timeout counter.
- `main.c` uses `DWT->CYCCNT` for the existing CPU overlay and resets it in
  `avc__next_frame()`, so DWT should not be quietly reused as the camera timing
  base without a wider ownership cleanup.

Timing direction:

Use the existing 1 ms `e_tick` for stable FPS and health summaries. If we need
sub-millisecond VSYNC period, jitter, or DMA latency, add a separate free-running
timer sampled in the VSYNC ISR, or use CTIMER capture through INPUTMUX if the
route is clean enough.

OSTIMER follow-up:

The MCXN947 reference material found locally describes OSTIMER as a 42-bit
Gray-code OS Event Timer. The clock tree can select `clk_16k[2]`,
`xtal32k[2]`, `clk_1m`, or no clock for OSTIMER, and the SDK clock API exposes
`kCLK_1M_to_OSTIMER` plus `CLOCK_GetOstimerClkFreq()`.

This makes OSTIMER a good candidate for the higher-resolution software
timestamp source if we clock it from `clk_1m` and sample it inside the VSYNC and
DMA callback paths. It is probably not a direct hardware capture replacement for
CTIMER: the peripheral register description exposes event counter, local
capture, local match, and CPU control registers, but the local material does not
show VSYNC/P4_22 routing into OSTIMER capture. If we need true hardware edge
latching, CTIMER capture through INPUTMUX remains the candidate.

FlexIO FIFO conclusion:

The current backend uses all eight MCXN947 FlexIO shifters in receive/FIFO form.
Each shifter has a 32-bit buffer, so the effective FlexIO staging depth is
`8 * 4 = 32 bytes`. This matches the current DMA minor loop and the RT1010
FlexIO camera reference driver, which drains 32 bytes per DMA request from the
first shifter buffer. There is no additional hidden FlexIO FIFO in this setup.

`SHIFTERR` is the important overrun evidence: in receive mode it is set when new
data would be stored before the previous `SHIFTBUF` data is read, or on a
start/stop-bit mismatch. The next firmware cleanup should preserve a latched or
cumulative `SHIFTERR` history instead of relying only on the instantaneous
register value printed in RTT.
