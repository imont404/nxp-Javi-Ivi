# Log: byte-parity

**Byte-parity established.** The standalone Arm GNU toolchain produces
functionally identical firmware to the MCUXpresso-bundled one. Every differing
byte is explained.

## Method

Built the Rev A competition image twice from the same source, differing only in
toolchain:

| | toolchain | text |
|---|---|---|
| A | `C:/nxp/MCUXpressoIDE_25.6.136/ide/tools/bin` (forced via `AVC_ARM_TOOLCHAIN_DIR`) | 245388 |
| B | `out/toolchains/arm-gnu-toolchain-14.2.rel1-...` (auto-discovered) | 245384 |

**Delta: 4 bytes.**

Both report the identical compiler version:

```
arm-none-eabi-gcc.exe (Arm GNU Toolchain 14.2.Rel1 (Build arm-14.52)) 14.2.1 20241119
```

## The 4 bytes

The compilers are the same build. The difference is inside the **prebuilt
newlib**, which embeds its own source path in assertion strings:

| | embedded path |
|---|---|
| MCUXpresso newlib | `/data/jenkins/workspace/GNU-toolchain/`**`arm-14-5`**`/src/newlib-cygwin/...` |
| Standalone newlib | `/data/jenkins/workspace/GNU-toolchain/`**`arm-14`**`/src/newlib-cygwin/...` |

Two strings (`dtoa.c` and `mprec.c`), two characters shorter each = **exactly 4
bytes**. Those two files are newlib's float-formatting code, which is consistent
with the earlier finding that `%.2f` in the overlay pulls in `malloc`.

## Verification that nothing else differs

Normalising the path string and comparing byte-wise leaves **35 differing
bytes**, all accounted for:

- **34 are pointers into the string table**, shifted by exactly **+2** (after
  the first shortened string) or **+4** (after both). Delta histogram:
  `{+2: 17, +4: 17}`.
- **1 is a comparison artifact.** At `0x03be80` the mcux image is still inside
  `_ctype_`, while the standalone image has `.text` ending 4 bytes earlier so
  that address is already `__exidx_start`. The byte-wise compare straddled a
  section boundary between images of different length.

**No functional difference. No code difference. Only a vendor build-path string
and the pointers that reference it.**

## What this licenses

The `build-reproduces` exit criterion is met — "byte-for-byte, or every
difference explained and accepted." This is the second case, and the explanation
is complete rather than hand-waved.

Practically: **MCUXpresso is no longer needed to produce the competition image.**
The remaining dependency is the generated source list, which is
`own-the-source-list`, not the toolchain.

## Reproducing

```powershell
.\setup.ps1                                     # provision the standalone toolchain
.\build_cmake.ps1 -BuildDir build\cmake\a       # uses the standalone toolchain
$env:AVC_ARM_TOOLCHAIN_DIR = "C:/nxp/MCUXpressoIDE_25.6.136/ide/tools/bin"
.\build_cmake.ps1 -BuildDir build\cmake\b       # uses MCUXpresso
Remove-Item Env:\AVC_ARM_TOOLCHAIN_DIR
```
