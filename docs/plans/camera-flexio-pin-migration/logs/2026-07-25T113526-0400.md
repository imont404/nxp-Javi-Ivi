# Log: backend-switch-parity

**Backend selection is now a software switch.** Both capture backends verified
on one physical harness with no rewiring between them.

## What was done

With the three `J9_EXT` jumpers left in place and **no hands on the hardware**
at any point:

1. Flashed the default Rev A EZH image (`avc_core0-Debug`).
2. Flashed the Port 1 FlexIO image (`avc_core0-FlexIOPort1`).

Two switches, both directions.

## Results

**EZH build** — boots clean:

```
Camera capture backend: SMARTDMA_EZH
bunny_build pass 1 / pass 2 -> All done
EZH interface configured
```

The EZH path emits no frame telemetry over RTT, so its capture evidence is the
LCD. **Operator confirmed a good image.**

**FlexIO Port 1 build** — unchanged from the first run:

```
cam_dma fps=23.39 done=269(+24) start=270(+24)
        timeout=0(+0) submit_err=0(+0) cb_err=0(+0) shiftstat=00 shifterr=00
        sample_nz=64 first=20E2,3164,31A5,39C5
```

**Operator confirmed a good image** here too.

23.39 fps, zero errors, `done` one behind `start` for the in-flight transfer —
identical to the pre-round-trip capture. Switching to EZH and back left no
residue.

## What this establishes

The headline claim of the plan holds: **`P1_4..P1_11` serves both backends, and
the choice is alt7 versus alt6 in firmware.** Three jumpers, no rewiring, and
the jumpers demonstrably do not disturb EZH.

## Exit criteria met

- `software-only-switch` — backend selection is alt7 versus alt6 on identical
  wiring, with no rewiring between builds.

Note `jumpers-non-destructive` was already met at fit time; this run reconfirms
it after two reflashes.
