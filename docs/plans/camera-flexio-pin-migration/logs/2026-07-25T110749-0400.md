# Log: port4-regression

**Port 4 hardware regression skipped by owner decision** — rewiring eleven
fly-wires to re-prove a path we are moving away from is not worth it. Going
straight to Port 1.

## Consequence, stated plainly

The refactor touched working capture code. Without the Port 4 hardware test, a
Port 1 failure is ambiguous: it could be the refactor or it could be the
wiring. Two things were done to narrow that gap.

## 1. Static comparison against the pre-refactor build

Built the Port 4 FlexIO image from the parent commit in a throwaway worktree
and compared.

- Text: 249640 pre versus 249580 post. Not byte-identical, and it was never
  going to be — the pin-configuration loop genuinely restructured from one
  ten-iteration sweep into an eight-iteration data loop plus explicit PCLK and
  HREF calls.
- Call-site profile differs only in `CLOCK_EnableClock` (2 -> 5, three of which
  are redundant repeats of the same two Port 4 clocks, and enabling a clock
  twice is idempotent) and `PORT_SetPinConfig` (2 -> 4 call sites, same pins).
- Comparing immediate constants was attempted and abandoned as uninformative:
  loop restructuring changes offsets and bounds for legitimate reasons, so the
  diff is noise.

**One real semantic delta was found and fixed.** The original cleared both the
HREF and VSYNC stale interrupt flags via `CAMERA_DIAG_IRQ_MASK`; the refactor
cleared only VSYNC. Restored as `CAMERA_FLEXIO_SYNC_CLEAR_MASK`. HREF and VSYNC
share a GPIO instance in both groups (GPIO4 for Port 4, GPIO0 for Port 1), so
one mask works for both.

**What this establishes:** the configured pin set is identical for Port 4
(P4_12..P4_21 as FlexIO alt6, P4_22 as GPIO), and the default Rev A EZH image
is still byte-identical at 245020 text, so there is no collateral damage
outside the FlexIO path. **What it does not establish:** that Port 4 still
captures on hardware. That remains unverified and will stay that way.

## 2. Pin-mux readback added

`camera__configure_flexio_edma_pins()` now reads the PCR MUX fields back and
reports them over RTT:

```
FlexIO camera pin mux readback: data(D7..D0)=0x66666666 pclk=6 href=6 vsync=0 OK
```

Expect alt6 on all eight data pins plus PCLK and HREF, alt0 on VSYNC, and the
literal `OK`. Anything else prints `UNEXPECTED`.

This is the substitute for the skipped regression: if Port 1 capture fails, the
readback immediately separates "the pins were not muxed as this build intended"
from "they were, and the problem is wiring or FlexIO configuration". That is
exactly the ambiguity the Port 4 test would have removed.
