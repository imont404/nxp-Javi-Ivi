# Log: jumper-fit

Three `J9_EXT` jumpers fitted on the test board and powered up with the **EZH
build unchanged**. Camera data is clean.

Jumpers as specified:

- pin 12 (`P3_4`, cam D4) -> pin 32 (`P1_8`)
- pin 11 (`P3_5`, cam D5) -> pin 30 (`P1_9`)
- pin 15 (`P0_5`, PCLK)   -> pin 2  (`P1_14`)

No cuts. R173 not removed.

## What this establishes

**The change is non-destructive.** EZH capture is unaffected by the jumpers, so
the fallback path is intact and the competition image is not at risk. Exit
criterion `jumpers-non-destructive` is met.

**The 330 ohm MCU-Link contention on P1_8 is probably a non-issue.** Worth
reasoning through, because it is not obvious: once jumper 1 is fitted, the
`P3_4` and `P1_8` nets are electrically **the same net**. Camera D4 is therefore
already driving into MCU-Link TX through R173's 330 ohm right now. EZH reads
that same net at `P3_4` and sees clean data, which means the camera is winning
that fight without corrupting the signal. That is real evidence R173 does not
need removing.

Caveat: this is at the current PCLK and at EZH's sampling point. It is
suggestive, not conclusive, for the FlexIO build where `P1_8` is the pin
actually sampled.

## Not yet established

- No formal `baseline-capture` numbers were recorded before fitting. The EZH
  path is known-good by observation rather than by a written frame-rate and
  reference-image baseline. Capture the Port 4 FlexIO baseline before the
  refactor so the Port 1 group has something to be measured against.
- PCLK stub behaviour is untested: EZH still takes PCLK via INPUTMUX from
  `P0_5`, so the `P1_14` jumper is currently just an unread stub on that net.
- Nothing about the Port 1 FlexIO path is proven yet; that needs the pin-group
  selector and the port decoupling work first.
