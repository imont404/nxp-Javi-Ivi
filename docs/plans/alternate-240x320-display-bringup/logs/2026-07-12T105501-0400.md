# Log: Started Parallel EZH I/O Map

Captured the first proposed ER-TFT020-7 parallel LCD I/O mapping.

Confirmed data-bus direction:

- Reuse the original shared camera/LCD data nets for LCD `D0..D7`.
- These map to `P1_4`, `P1_5`, `P1_6`, `P1_7`, `P3_4`, `P3_5`, `P1_10`, and
  `P1_11`.
- They line up with `SMARTDMA_PIO0..7`, so they are a good EZH byte lane.
- This is separate from the current FlexIO camera validation data bus on
  `P4_12..P4_19`.

Control-signal notes:

- Proposed reset reuse is `P1_19`, the old camera reset net. This is also
  already named `EZH_LCD_D15_CAMERA_RST` and has `SMARTDMA_PIO15` available.
- The proposed pin-exact `WR`/`RS` reuse is `WR=P0_4` and `RS=P0_11`.
- The old sync-net labels still need one confirmation before Rev B routing:
  the netlist names `P0_11` as old camera HSYNC and `P0_4` as old camera VSYNC,
  but the proposed text paired those names with the opposite pins.
- Existing design-file LCD controls remain possible alternatives:
  `P2_0/EZH_LCD_WR`, `P1_22/EZH_LCD_DC`, and `P4_4/EZH_LCD_CS`.

Implementation sequence decision:

- Take a CM33 C bit-bang baby step before the EZH port.
- Use the same candidate 8080 bus pins, conservative software delays, and a
  fixed RGB565 pattern to validate straps, wiring, byte order, `WR`, `RS`,
  `CS`, and `RD`.
- After that proof works, port the known-good write sequence to a bounded
  EZH/bunny program with explicit `WR` pacing, `EZH2ARM` completion, and halt.

Open before wiring/code:

- Resolve whether `WR` is `P0_11` or `P0_4`.
- Resolve whether `RS` is `P0_4` or `P0_11`.
- Decide the `CS` pin or whether scoped proof bursts can hold CS active.
- Decide how `RD` is held inactive for write-only operation.
