21.1.1 Module instances
This device has one instance of the CoolFlux BSP32 module, BSP32_0.
21.1.2 RAM
CoolFlux program memory interface can access flash and FlexSPI also along with RAMX, RAMA ~ RAMH. CoolFlux X data 
memory interface can also access mailbox and Powerquad RAM.
21.1.3 Compiler options
Due to long memory paths from data memory output directly to data memory address, the maximum frequency that can be 
obtained is limited. The compiler should disable the sequence that consists of a data memory load to a pointer register, followed 
in the next cycle by a memory access using that same pointer.
21.2 Overview
The CoolFlux BSP32 is a programmable digital signal processor, where BSP stands for Baseband Signal Processor and the 32 
indicates that is has a 32-bit data path and 32-bit data memories. It is dual Harvard, dual multiplier processor based on the ultra-low 
power CoolFlux architecture. It supports 16 and 32-bit scalar operations as well as complex and SIMD operations and data types. 
CoolFlux BSP32 is fully programmable in C and comes with an optimizing compiler and tool suite.
More information about the CoolFlux BSP32 can be received from the NXP CoolFlux team (coolflux.support@nxp.com). 
Documentation on the tools (compiler, simulator, linker, ...) as well as documentation on the architecture and instruction set 
architecture are available as well. Training on programming the CoolFlux BSP32 processor can also be requested using the same 
channel and email address.
This module has a dedicated clock and reset signal.

21.3 Functional description
The CoolFlux BSP32 subsystem is built around the CoolFlux BSP32 processor as the main building blocks. This is a fully (C) 
programmable architecture that is able to execute a wide range of different algorithms. All other modules within the subsystem 
are meant to control this processor or to enable external communication towards the CoolFlux BSP32.
The interrupt controller can be used to interrupt the CoolFlux BSP32 based upon external events. In the other direction, the 
CoolFlux BSP32. also has the ability to send interrupts externally which allow inter-processor communication.
A cross-break module is available which allows common debugging between the Cortex processor and CoolFlux BSP32. This 
cross-break is able to transfer break events between both processors which allow a processor to (conditionally) enter debug mode 
at the moment the other one does.
A range of programmable registers (within the APB addressing space) is to configure and initialize the CoolFlux BSP32. This 
includes setting memory offset registers and inter-processor communication registers as will be explained later in the register 
definition chapter.
21.3.1 Security
CoolFlux BSP32 does not include any mechanism for supporting system security of the type implemented by the Cortex-M33.
21.3.2 APB programming interface
The CoolFlux BSP32 subsystem has an APB programming interface that is used to configure the subsystem. It is used to set the 
memory offset registers, program the internal FIFO’s, set the boot address, and generate an interrupt towards CoolFlux BSP32. 
Most of these registers must be set before the subsystem is pulled out of reset.
21.3.3 Cross break
The CoolFlux BSP32 subsystem contains a programmable cross break module that makes it possible to do co-debugging 
between CoolFlux BSP32 and Cortex M33. It can, for instance, be used to stop one processor when the other one hits 
a breakpoint.
21.3.4 Inter-CPU communications
CoolFlux BSP32 and CM33 can communicate with each other via various means. Shared memory that is accessible to both 
processors makes it possible to work on shared buffers. The mailbox can be used to send messages from one processor to the 
other. Finally, both processors can generate interrupts on the other one.
21.3.5 Operations and modes
The CoolFlux BSP32 is a programmable architecture that is initialized through a range of programmable registers in APB 
addressing space. It always executes its program via program memory and accesses the data within X or Y memory space. Hence 
it has no different operations or modes. 
21.3.6 Clocking
The CoolFlux BSP32 has a single clock input pin called "clk". Only the rising edge of this clock is used. Note that the APB 
programming interface and the APB debug interface have their own APB clock signals, called "apb_pclk" and "apb_pclk_debug" 
respectively, both asynchronous and active low.
21.3.7 Reset
The CoolFlux BSP32 is held in reset after a device reset. Before CoolFlux BSP32 begins execution, the Cortex-M33 must load 
code into the memories accessible by the CoolFlux BSP32, configure CoolFlux BSP32 configuration registers (for instance, the 
memory offset values), and release the CoolFlux BSP32 from reset. The reset input signal is called "reset" and is asynchronous, 
active high. Note that the APB programming interface and the APB debug interface have their own APB reset signals, called 
"apb_presetn" and "apb_presetn_debug" respectively, both asynchronous and active low.

21.3.8 Interrupts
CoolFlux BSP32 has 32 external interrupt inputs. An internal interrupt controller maps these 32 interrupt sources to any of the 
three CoolFlux interrupt routines. Each interrupt can be enabled or disabled individually and routed to any interrupt routine. The 
interrupts are handled in software by the processor itself using edge detection. Whenever an interrupt is received on the CoolFlux 
BSP32, the corresponding interrupt routine is executed.
More explanation on the usage of interrupts can be found in the CoolFlux documentation that can be obtained from the CoolFlux 
team (coolflux.support@nxp.com).
The CoolFlux BSP32 subsystem can generate an external interrupt. This interrupt can be routed towards the Cortex M33 to 
facilitate inter-processor communication.
21.4 External signals
This section explains the external signals. The CoolFlux BSP32 subsystem has the following interface groups
External signals:
• Clock, reset and test signals
• APB programming interface
• APB debug interface
• Cross-trigger interface
• Interrupt interface
• Sleep mode indication
• Program memory AHB-Lite interface
• X-data memory AHB-Lite interface
• Y-data memory AHB-Lite interface
21.5 Initialization
Before the CoolFlux BSP32 subsystem can be used, it must be initialized. This involves the following.
Initialization:
• The three memories (P,X,Y) must be loaded with the correct program and data
• The four IVT registers (registers ivt0, ivt1, ivt2, ivt3) must be initialized
• The APB configuration registers must be initialized (e.g. offset registers to be able to access the memories)
• Clock must be enabled
• Reset must be de-asserted
From this moment onwards, the CoolFlux BSP32 will start executing the code as placed inside the program memory.
21.6 Application information
The CoolFlux BSP32 subsystem is built around the CoolFlux BSP32 processor. As this is a fully C-programmable processor, 
it can be used to execute different sorts of applications. These can be audio application, baseband algorithms, ultra-wide band 
applications. It is optimized to efficiently run integer, fix-point and complex data types in an ultra-low power manner.

The CoolFlux BSP32 includes three AHB-Lite bus master interfaces. The priority of this and other AHB bus masters can be 
adjusted to achieve system performance needed by an application by using the SYSCON[AHBMATPRIO] register.
21.7.1 RAM
The CoolFlux BSP32 AHB-Lite program memory interface can access the SRAM X memory as well as SRAM A … SRAM 
H memory.
The X and Y CoolFlux BSP32 AHB-Lite data memory interfaces can access the SRAM A … SRAM H memories. These data 
memories also have access to the PowerQuad addressing space.
21.7.2 AHB and APB peripherals
The CoolFlux BSP32 processor access to peripherals is limited to the Inter-CPU mailbox attached to the AHB bus. This way, it 
is possible to communicate through short messages and interrupts between the CoolFlux BSP32 and the Cortex M33. Refer to 
the Inter-CPU Mailbox chapter for more information.

initialized using the APB interface. Communication between the CoolFlux BSP32 subsystem and the Cortex subsystem also 
uses this interface.

Function
The Interrupt Vector Table (IVT) of the CoolFlux BSP32 is used to determine the addresses of the reset vector and interrupt 
vectors. By default, the IVT table starts from program memory address 0 from a CoolFlux point of view, which means that 
the IVT start address is defined by the "offset address for program memory" register. The IVT offset register can be used 
to re-locate the IVT table of the CoolFlux BSP32 program, thereby placing the IVT table in a different location in program 
memory. For more information about the IVT table, please refer to the CoolFlux BSP32 C Programmer's manual that can be 
obtained from the CoolFlux team (coolflux.support@nxp.com).

21.8.10 CoolFlux BSP32 sleep mode register (sleep_mode)
Offset
Register
Offset
sleep_mode
20h
Function
Register indicating whether the CoolFlux BSP32 is in sleep mode (1) or not (0). The CoolFlux BSP32 will enter sleep mode 
when the eop (End-Of-Program) instruction is executed and is thus fully under software control. It will exit from sleep mode in 
case of an interrupt request, debug request or a full reset. Sleep mode is used in an application to save power while waiting on 
a particular event (mostly an interrupt as mentioned above). In this sleep mode, power consumption is reduced as most of the 
clocks will be switched off (automatically done in hardware).

This block is a AHB slave peripheral with a single clock domain and reset. This device supports two mailboxes, where each 
mailbox has three 32-bit registers. Each mailbox has one mutex register and one peripheral ID register. For each mailbox, the 
corresponding interrupt line intr[i] is set if MBOX_REG[i] is not 0 and cleared if it is 0.
22.1.1 Module instances
This device has one instance of the Inter-CPU Mailbox module, MAILBOX0.
22.2 Overview
MAILBOX provides simple communication and resource allocation between CPUs by using two mechanisms:
The first mechanism helps you send an interrupt, along with a simple message, to another CPU. To generate an interrupt 
to another CPU, you can set any one of the interrupt flags (up to 32) by using Cortex-M33 (CPU0) Interrupt Set (IRQ0SET) 
and Cortex-M33 (CPU1) Interrupt Set (IRQ1SET). The other CPU reads Cortex-M33 (CPU0) Interrupt Set (IRQ0SET) and 
Cortex-M33 (CPU1) Interrupt Set (IRQ1SET) to determine the action it needs to perform. If more than one IRQn field is 1, the CPU 
receiving the interrupts reads all of them. After completing the requested service or operation, the CPU that receives the interrupt 
requests writes 1 to one or more fields in Cortex-M33 (CPU0) Interrupt Clear (IRQ0CLR) and Cortex-M33 (CPU1) Interrupt Clear 
(IRQ1CLR) to clear them.
To check whether the operation is complete, the CPU sending the request can check IRQn, or the CPU receiving the original 
interrupt can use the same mechanism on the reverse to notify the requesting CPU.
You can determine the use of each bit in Cortex-M33 (CPU0) Interrupt (IRQ0) and Cortex-M33 (CPU1) Interrupt (IRQ1) and also 
provide additional information to each request bit. For example, both the CPUs can use predefined memory locations to hold 
detailed information about the interrupt requests.
The second mechanism is based on a single-bit resource allocation request. MUTEX[EX] defines the mutual exclusion request, 
and reading it provides the current status of the resource. If the resource is available, it is reserved for the process that reads the 
register. You define the resource control, and after getting access to the resource, you must write 1 to MUTEX[EX] to clear the 
field after it has used the resource. For more information, see MUTEX[EX].

22.5.1.8
Mutual Exclusion (MUTEX)
Offset
Register
Offset
MUTEX
F8h
Function
Provides an inter-processor communication handshake.
This register provides a resource allocation handshake between two CPUs. To access a shared resource (possibly a resource 
allocation table in memory), a CPU reads this register. If the CPU reads 1, it has control over the shared resource allocation. 
After making the required changes, the CPU writes to the register. As a result, MUTEX[EX] becomes 1 again, making the shared 
resource allocation available to another CPU. If the CPU reads 0, it must wait for MUTEX[EX] to become 1 before accessing the 
shared resource allocation information.
