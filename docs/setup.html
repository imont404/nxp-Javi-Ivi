AVC – Setup and Build

Updated 2026-07-25. This is the page to read first. It assumes you have never seen this repository and have nothing installed.

Getting started, from nothing

Three commands. The first one is slow; the other two are not.

.\setup.ps1                              once per machine, ~5 minutes
cmake --preset competition               configure
cmake --build --preset competition       build

Then put the firmware on the board:

.\flash.ps1

And watch it run:

.\rtt.ps1 -Reset -Seconds 30

Both default to the competition preset. To use a different one, name it – you do not have to type a path:

.\flash.ps1 -Preset encoder-diag
.\rtt.ps1   -Preset encoder-diag -Reset -Seconds 30

If you name a preset that does not exist, the script says so and lists the real ones. If you name one you have not built yet, it tells you the two commands to build it rather than flashing an old image by mistake.

MCUXpresso is not required. It used to be. setup.ps1 downloads a standalone Arm compiler instead, and the build was verified to produce the same firmware either way – see Toolchain provisioning below.

What setup.ps1 installs

ToolUsed forWhere it goes
Arm GNU Toolchain 14.2.Rel1compiling the firmwareout\toolchains\ in this repository
CMakethe build systemwinget, system-wide
Ninjathe thing that actually runs the compilerwinget, system-wide
uvPython tooling for the quality gateswinget, system-wide
LLVMclang-format and clang-tidywinget, system-wide

It is safe to run more than once – anything already present is skipped. It does not change your PATH and does not set environment variables. The Arm toolchain lives inside the repository under out\, which is git-ignored; deleting that folder and re-running setup.ps1 puts it back.

If winget is blocked – common on managed or work laptops – setup.ps1 will say which tools it could not install and carry on. The Arm toolchain is downloaded directly and does not need winget, so the firmware will still build as long as CMake and Ninja are available. Install the rest by hand and run setup.ps1 again to confirm.

Build variants

Variants are CMake presets, not separate scripts. List them:

cmake --list-presets
PresetWhat it isHardware needed
competitionThe race image. Start here. EZH camera capture, SPI LCD, USB stream off, encoders off.the car as built
encodersCompetition image plus wheel-speed feedback and the on-screen RPM readout.the car as built
flexio-port1Camera capture through FlexIO instead of the EZH, on the existing camera wiring.three jumpers on J9_EXT
flexio-port4The original FlexIO pin group.eleven fly-wires
servo-p3-20Competition image driving the servo from the Rev B candidate pin.scope on shield J1.5
encoder-diagEncoder bench diagnostic, motors off. RTT only, no camera or LCD.turn the wheels by hand
encoder-diag-motorsSame, but drives the motors at 10% and auto-starts.car on blocks

Build any of them the same way:

cmake --preset <name>
cmake --build --preset <name>

The image always lands at build\cmake\<name>\avc_core0.axf.

encoder-diag-motors spins the wheels four seconds after reset, without being asked. Put the car on blocks. Duty is capped at 20% by a compile-time check, but a car on the floor will still drive away.

Editing: VS Code

Open the repository folder in VS Code. It will offer to install the C/C++ and CMake Tools extensions; accept. Pick a preset from the status bar and build from there if you prefer buttons to commands.

IntelliSense reads compile_commands.json from the competition build, so configure that preset at least once or headers will appear unresolved:

cmake --preset competition

Format-on-save is deliberately off. The firmware carries a mix of tabs and spaces inherited from the NXP SDK, and reformatting on save produces enormous whitespace-only diffs.

Flashing, RTT, setup, and the drift check are also available as VS Code tasks (Terminal → Run Task).

Toolchain provisioning

The build finds a compiler in this order:

  1. -DAVC_ARM_TOOLCHAIN_DIR=<path to bin>
  2. the AVC_ARM_TOOLCHAIN_DIR environment variable
  3. the toolchain setup.ps1 put in out\toolchains\
  4. the compiler bundled with MCUXpresso, if it happens to be installed

MCUXpresso is a fallback, not a requirement. The version setup.ps1 downloads is the same one MCUXpresso 25.6 bundles (14.2.Rel1), which is what makes the two comparable.

They were compared. Building the competition image with each toolchain differs by exactly four bytes, and those four bytes are a build path that NXP's copy of the C library has baked into it (…/arm-14-5/… where Arm's says …/arm-14/…). Everything else is identical. There is no functional difference between a build made with either compiler.

Quality gates

One command says whether the tree is in good shape:

uv run rack run          everything
uv run rack run L99      the signoff gate only
StratumChecksNeeds
L0_foundationThe build definitions are present and self-contained: presets, the checked-in source list, the vendored header, the linker captures.nothing
L1_buildThe competition image compiles, and the source list has not drifted from the MCUXpresso project metadata.a toolchain
L2_qualityComplexity against docs/quality/lizard-baseline.txt.uv
L99_signoffGovernance audit, and that the student entry points and competition defaults are intact.uvx

Building every preset is slow, so it is opt-in:

$env:AVC_TEST_ALL_PRESETS = "1"
uv run rack run L1
Complexity is a tracked baseline, not a cliff. Existing debt does not fail the gate; making something worse does. If you deliberately accept a more complex function, regenerate docs/quality/lizard-baseline.txt and say why in the commit.

Governance checks alone, without the suite:

uvx --from wn-dev-std==2026.7.18 dev-std audit . --scope docs.plans

Formatting

.clang-format exists but is not applied across the tree – reformatting the NXP SDK sources would bury every real change in whitespace. Use it on files you are already editing:

clang-format -i src\avc\avc_core0\source\<file>.c

Conventions worth knowing

The source list is checked in

src\avc\avc_core0\cmake\mcuxpresso_debug.cmake lists every source file. It was originally generated from the MCUXpresso project files, but it is committed and used as-is, so a normal build needs neither Python nor MCUXpresso.

If you change the project settings in MCUXpresso, that file can fall out of date. Check and update it explicitly:

.\build_cmake.ps1 -CheckDrift    show what changed, write nothing
.\build_cmake.ps1 -Regenerate    accept it, then review and commit

The linker scripts are captures

src\avc\avc_core0\link\ holds copies of the linker scripts MCUXpresso would otherwise generate into Debug\. They are the source of truth, and each carries a header saying so.

One is deliberately edited: the MCUXpresso original pulls in libcr_newlib_nohost.a, which ships only with the IDE. It was replaced with the standard libnosys.a. That change removed the bounded heap NXP's library provided, so source\shared\avc__sbrk.c restores it. If you regenerate and diff, expect to see exactly that one library line differ.

Vendored headers

source\shared\cr_section_macros.h is copied from the MCUXpresso install because the firmware needs it for memory placement – it is what puts the camera frame buffers where they belong. Do not edit it.

Older scripts

build_cmake.ps1 still works and does the same thing as the competition preset. It remains for the drift check and for anything that already referenced it. New work should use presets.

build.ps1 drives MCUXpresso headlessly and is the fallback if the CMake build ever fails in a way that needs the IDE to diagnose.
