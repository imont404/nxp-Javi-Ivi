NXP Cup – Setup and Build

Structure migration notice (2026-08-25): this page is awaiting the scheduled documentation rewrite. Do not use the legacy commands below. Use the repository README and source component map for the current setup and build entry points.

Getting started, from nothing

Two commands. The first one is slow; later builds reuse the installed tools.

.\setup.ps1                              once per machine, ~5 minutes
.\build.ps1                              configure and build the competition image

That produces the firmware image here:

build\cmake\competition\nxp_cup_core0.axf
bin\firmware\nxp_cup_core0.axf

The first path is the authoritative CMake output. The root build.ps1 wrapper also copies the AXF and BIN into the shorter bin\firmware path.

Flashing is done with Segger Ozone, using the project in src\nxp_cup\nxp_cup_core0\ozone__core0.jdebug. See the Ozone section of README.md for installing it and connecting to the board.

The car should come up with live camera on the LCD. That is the loop you will spend the week in: edit, build, flash, look at the screen.

If you name a preset that does not exist, CMake says so and lists the real ones.

Seeing what the car is thinking

You have two windows into a running car, and neither needs a debugger:

  • The on-board LCD shows the live camera image. You can draw on it – the frame buffer is yours, so overlay the pixels your algorithm is actually looking at, mark the track centre you computed, and you will see it move as the car sees.
  • The USB stream sends the same frames to a PC when you turn it on, which is easier to study than a small screen bolted to a moving car.
Drawing costs time. You have about 41 ms per frame to decide a steering angle. Text rendering in particular is not free. If you overlay too much, you will blow the frame budget and the car will drive worse than the one that drew nothing – which is a real lesson, and cheaper to learn here than on the track.
MCUXpresso is not required. It used to be. setup.ps1 downloads a standalone Arm compiler instead, and the build was verified to produce the same firmware either way – see Toolchain provisioning below.

It is safe to run more than once – anything already present is skipped. It does not change your PATH and does not set environment variables. The Arm toolchain lives inside the repository under out\, which is git-ignored; deleting that folder and re-running setup.ps1 puts it back.

If winget is blocked – common on managed or work laptops – setup.ps1 will say which tools it could not install and carry on. The Arm toolchain is downloaded directly and does not need winget, so the firmware will still build as long as CMake and Ninja are available. Install the rest by hand and run setup.ps1 again to confirm.

One firmware image

There is one normal build: competition. It includes the EZH camera, SPI LCD, session-gated scalar/text USB telemetry, and QDC wheel-speed feedback. QDC is standard operating procedure, not an optional build setting. Run .\build.ps1; students do not choose among hardware presets.

Direct CMake remains available for IDE integration and automation:

cmake --preset competition
cmake --build --preset competition

Organiser-only FlexIO and encoder diagnostics remain under scripts\maintainer. They use separate output directories and do not appear in the student preset list.

Optional PC and Android applications

To build the native SDL2/Dear ImGui USB camera/telemetry viewer, run:

.\build_viewer.ps1

The viewer displays framework-owned mode, state, actuator commands, and participant telemetry in stable named rows. Text telemetry values are limited to 48 UTF-8 bytes.

The runnable viewer bundle is copied to bin\host\; start it with .\bin\host\nxpc_viewer.exe. Root setup.ps1 installs LLVM-MinGW for this build; Visual Studio C++ is not required.

The Android USB bridge has a separate, explicit maintainer setup because the Android SDK licenses must be accepted:

.\scripts\android\setup_android.ps1 -AcceptLicenses  once per workstation
.\build_android.ps1                                  unit tests + debug APK
.\build_android.ps1 -Offline                         after one connected build

The setup script installs pinned JDK 17, Android SDK Platform 35, Build Tools 35.0.0, ADB, and Gradle 8.9 under out\toolchains\android. Gradle dependencies are cached there as well. Nothing is installed globally and no environment variables are persisted. The APK is copied to bin\android\nxp_cup_bridge.apk.

Editing: VS Code

Open the repository folder in VS Code. It will offer to install the C/C++ and CMake Tools extensions; accept. Select the competition preset if the extension asks, or build with .\build.ps1 in a terminal.

IntelliSense reads compile_commands.json from the competition build, so configure that preset at least once or headers will appear unresolved:

cmake --preset competition

Format-on-save is deliberately off. The firmware carries a mix of tabs and spaces inherited from the NXP SDK, and reformatting on save produces enormous whitespace-only diffs.

VS Code is the editor and nothing more here. There are no build tasks, run buttons, or debug configurations checked in, and that is deliberate: you build in a terminal and flash in Ozone, so there is one way to do each thing rather than two that can disagree.

Toolchain provisioning

The build finds a compiler in this order:

  1. -DNXPC_ARM_TOOLCHAIN_DIR=<path to bin>
  2. the NXPC_ARM_TOOLCHAIN_DIR environment variable
  3. the toolchain setup.ps1 put in out\toolchains\
  4. the compiler bundled with MCUXpresso, if it happens to be installed

MCUXpresso is a fallback, not a requirement. The version setup.ps1 downloads is the same one MCUXpresso 25.6 bundles (14.2.Rel1), which is what makes the two comparable.

They were compared. Building the competition image with each toolchain differs by exactly four bytes, and those four bytes are a build path that NXP's copy of the C library has baked into it (…/arm-14-5/… where Arm's says …/arm-14/…). Everything else is identical. There is no functional difference between a build made with either compiler.

Quality gates

One command says whether the tree is in good shape:

uv run rack run          everything
uv run rack run L99      the signoff gate only
StratumChecksNeeds
L0_foundationThe build definitions are present and self-contained: presets, the checked-in source list, the vendored header, the linker captures.nothing
L1_buildThe competition image compiles, and the source list has not drifted from the MCUXpresso project metadata.a toolchain
L2_qualityComplexity against docs/quality/lizard-baseline.txt.uv
L99_signoffGovernance audit, and that the student entry points and competition defaults are intact.uvx

Building every preset is slow, so it is opt-in:

$env:NXPC_TEST_ALL_PRESETS = "1"
uv run rack run L1
Complexity is a tracked baseline, not a cliff. Existing debt does not fail the gate; making something worse does. If you deliberately accept a more complex function, regenerate docs/quality/lizard-baseline.txt and say why in the commit.

Governance checks alone, without the suite:

uvx --from wn-dev-std==2026.7.18 dev-std audit . --scope docs.plans

Formatting

.clang-format exists but is not applied across the tree – reformatting the NXP SDK sources would bury every real change in whitespace. Use it on files you are already editing:

clang-format -i src\nxp_cup\nxp_cup_core0\source\<file>.c

Conventions worth knowing

The source list is checked in

src\nxp_cup\nxp_cup_core0\cmake\mcuxpresso_debug.cmake lists every source file. It was originally generated from the MCUXpresso project files, but it is committed and used as-is, so a normal build needs neither Python nor MCUXpresso.

If you change the project settings in MCUXpresso, that file can fall out of date. Check and update it explicitly:

.\scripts\maintainer\build_cmake.ps1 -CheckDrift    show what changed, write nothing
.\scripts\maintainer\build_cmake.ps1 -Regenerate    accept it, then review and commit

The linker scripts are captures

src\nxp_cup\nxp_cup_core0\link\ holds copies of the linker scripts MCUXpresso would otherwise generate into Debug\. They are the source of truth, and each carries a header saying so.

One is deliberately edited: the MCUXpresso original pulls in libcr_newlib_nohost.a, which ships only with the IDE. It was replaced with the standard libnosys.a. That change removed the bounded heap NXP's library provided, so source\shared\nxpc__sbrk.c restores it. If you regenerate and diff, expect to see exactly that one library line differ.

Vendored headers

source\shared\cr_section_macros.h is copied from the MCUXpresso install because the firmware needs it for memory placement – it is what puts the camera frame buffers where they belong. Do not edit it.

Older scripts

scripts\maintainer\build_cmake.ps1 still works and does the same thing as the competition preset. It remains for the drift check and for anything that already referenced it. New work should use presets.

build.ps1 is the competition build wrapper. Maintainers can run scripts\maintainer\build_mcuxpresso.ps1 when an IDE comparison is needed.
